# Synchro v0.3.0 Remediation And Debloat Plan

Date: 2026-08-21.
Authority: `docs/superpowers/plans/2026-08-21-v0.3.0-phase-1-5-audit.md` and `docs/superpowers/plans/2026-07-17-synchro-v0.3.0-verified-rc.md`.
This plan amends the master plan where the two conflict. The amendments are listed in the final section.

**Goal:** Reach a v0.3.0 release candidate with honest gates, a lean verification system, and hot paths that support the performance positioning, without a rewrite.

## Binding Rules For The Executing Agent

- Every validation claim must name the exact commit hash it ran on.
- A validation claim from a dirty worktree is invalid.
- A gate that can pass while executing zero tests is a defect. Fix the gate before the work it gates.
- Route every required gate through structured result parsing. A skipped test is a failure.
- Do not create a new abstraction in `conformance/` without naming its concrete consumer in the same change.
- Any change that grows `conformance/` must state what it deletes.
- Test code obeys the same simplicity rules as production code.
- Each behavior has one authoritative proof home. Do not add a second proof of a covered behavior in another layer.
- Do not report an intermediate step as phase completion. Do report intermediate progress honestly with its commit hash.
- Record findings, dispositions, and gate outputs in GitHub issues 34 and 35 as work proceeds.

# Phase R1: Correctness And Performance

R1 fixes the product. It is not a benchmarking phase.

- The correctness tasks remove user-facing defects.
- The performance tasks remove wasted work from the engine hot paths. They are product-side debloat.
- Every measurement compares Synchro against its own recorded baseline on fixed local hardware.
- No competitor system is deployed, installed, or measured in R1. Competitive claims are Phase R4.
- Fixes land in R1, before R2, because source changes invalidate generated evidence. The code changes while proofs are cheap. R2 then generates the expensive evidence once, against the corrected engine.
- The benchmark gate lands in R1 so its stored baseline protects the hot paths during the R2 deletions.

# Phase R2: Phase 5 Restructure And Structural Debloat

## Phase 5 restructure

This section replaces the master plan Phase 5 execution model.

- [ ] Run the full 14-scenario semantic corpus on three representative cells: Swift on current macOS, Kotlin on one current-API Android emulator or device, and React Native once per platform.
- [ ] Give every remaining support cell a packaged-install smoke gate: install the packaged artifact, connect, push, pull, kill the process, resume. Five checks per cell.
- [ ] Land scenario work scenario by scenario. The batch-only rule is deleted.
- [ ] Add `make phase-5-check` as the final aggregate over the three semantic cells, all smoke cells, packaged consumers, and the unfiltered unit and integration gates.
- [ ] Wire the Android instrumentation gate so Robolectric stops standing as native release evidence.
- [ ] Resolve the oracle gap. Either implement strict scenario-driven execution against the real server, or designate the `TestReal*` corpus as the official proof with a mechanical mapping from each test to its scenario and obligation IDs, plus a drift check that fails when a scenario has no mapped test.
- [ ] Build nothing new on the reference model. Native execution verdicts compare observed facts against authored scenario expectations and existing real-corpus checks. No new binding, gate, or evidence path may depend on `conformance/reference/` or `conformance/modelrunner/`.

# Phase R3: Oracle Replacement (post-0.3.0)

Do not start the deletion work before v0.3.0 ships. The replacement is seeded earlier so no work is built twice.

- [ ] Freeze `conformance/reference/` and `conformance/modelrunner/` now. No growth is permitted during R0 through R2, and no new work may depend on them.
- [ ] Build the Phase 6 soak divergence checker as the invariant-engine core: mutation conservation, cursor monotonicity, checksum convergence, scope isolation, and no state forks across process death. Assemble it from the existing verified digest and conservation validators. This checker is permanent code, not scaffolding.
- [ ] After release, migrate the remaining reference-model checks into the invariant engine.
- [ ] Drive the invariant engine from the seeded randomized soak. Every soak failure replays from its seed and becomes a permanent minimized scenario.
- [ ] Delete `reference/` and `modelrunner/` when the invariant engine demonstrably covers their checks, with a negative control per migrated invariant.

# Phase R4: Competitive Benchmark (gates public claims, not the release)

This phase gates marketing statements, not code. Run it before the first public competitive performance claim. v0.3.0 can ship without it. Until it runs, publish no comparative statement.

## Contract

- [ ] Compare Synchro against OSS PowerSync on one identical topology: both server stacks on the same Linux Docker host, clients on the same machine over the same network.
- [ ] Pin exact versions of both systems, all toolchains, and all seeds in a benchmark manifest.
- [ ] Configure PowerSync per its documented production guidance. A default-configuration or misconfigured comparison is invalid.
- [ ] Use two dataset sizes: approximately 1,000 rows and approximately 100,000 rows, with realistic row width of 15 or more mixed columns.
- [ ] Measure four metrics per system: initial sync time, steady-state incremental pull latency with approximately 1 percent changed rows, push throughput, and fresh-database rebuild time.
- [ ] Run each cell five times. Record median and spread.
- [ ] Publish the manifest, the harness, and the raw results with any claim, so the result is reproducible by a third party.

## Exit Gate

- Every published competitive statement traces to a specific measured cell in the manifest.
- A result that does not favor Synchro is recorded, not discarded. It becomes R-phase or backlog performance work.

# Target Test Architecture

Seven layers. Each behavior has one authoritative home.

1. Contract layer: the specification plus authored vectors consumed by every surface.
2. Unit layer: deterministic tests beside the code, with mocks only where the policy allows.
3. Real integration corpus: `TestReal*` and client integration suites against the real extension, adapter, and PostgreSQL.
4. Scenario corpus: the authored semantic scenarios on three representative cells. Every production defect becomes a permanent minimized scenario.
5. Cell smoke: the five packaged-install checks per remaining support cell.
6. Adversarial layer: mutation gates, negative controls, and mechanical zero-skip enforcement. This layer proves the other layers can fail.
7. Randomized soak: seeded generative workloads checked by invariants. This layer covers the space no enumeration can reach.

Layers 6 and 7 are what allow layers 1 through 5 to stay small.

# Amendments To The Master Plan

- The Phase 5 batch execution contract (one batch across 140 obligations) is deleted.
- The 140-obligation native matrix is replaced by three semantic cells plus per-cell smoke gates.
- The evidence system requirement is satisfied by CI logs on a named commit plus the summary generator. Signed receipts are not required.
- Line-count budgets are not used. The `AGENTS.md` Verification Simplicity rules govern size and structure.
- A public competitive performance claim requires the Phase R4 benchmark. Comparison against published third-party results is not accepted evidence for a claim.
- All other master plan requirements, including Phase 6 certification, soak, and artifact discipline, remain in force.
